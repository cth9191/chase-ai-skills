Running /loop-engineer — an example session

What it actually feels like to loop-engineer a task with the skill. Scenario: a weekly LinkedIn-article loop.

The flow: Diagnose → fast interview (each question with a recommended answer) → it builds the complete runnable loop for your task — skill, trigger, state, verification, stop rule, README. If your task is unproven, the loop's first run is a validation gate. It only refuses when something genuinely shouldn't be a loop.

loop-engineer · Q4 — success criteria (the heart)
Q4 / verification — push hard here

This is the make-or-break. How do we know an article is good? Walk the ladder with me:

Tier 1deterministic yes/no — doesn't exist for writing
Tier 2rule/constraint — "≥3 sources, <1300 words" (cheap guardrail, not quality)
Tier 3a number — engagement (likes/comments). Objective, but lagged + noisy
Tier 4a judge — an LLM scores craft pre-publish. Needed because likes lag days
Tier 5human-only — you eyeball before it posts (we'll keep this as a gate)
Recommend a hybrid: Tier 4 + Tier 3. A craft-judge scores the draft before posting; real engagement recalibrates over time. And the judge must be a different model than the writer — if Claude writes it, Codex judges it. Models love their own work; self-judging is worthless.
You
You

LE
loop-engineer · Q5 — the trap most people miss
Q5 / measurement lag

One catch with engagement: likes arrive days after you post. So a single Monday loop can't both write and learn from real numbers in the same run.

Recommend a second loop: a daily scraper that pulls each post's engagement and backfills the state store. The Monday writer then reads settled numbers from prior weeks. Without this, the loop optimizes on data that isn't in yet.
You
You

Didn't think of that. Add the scraper loop.

LE
loop-engineer · Q6 — state
Q6 / state — the self-improvement engine

Where does memory live, and what does each run read?

Recommend: a state.json logging per article — the angle, the hook, the CTA, the Codex score, and (backfilled) the real engagement. Each Monday the writer reads it first: "these hooks landed, these flopped — don't repeat the duds." That memory is the only thing separating a self-improving loop from 52 random shots a year.
You
You

Perfect.

LE
loop-engineer · Q7 — stop rule + sanity gate
Q7 / stop rule & honesty check

Two last things. A stop rule — and an honest gut-check on whether this should stay autonomous.

Recommend: keep a human publish gate (you approve before it posts — it's your name and reputation), plus a hard cap so a runaway research pass can't burn tokens. It's a loop, but a human-gated one. That's the right call for taste-driven, public-facing work.

You

Agreed, I want the final say.

# Loop Spec: weekly-linkedin-article

## Verdict: is this a loop?
YES — building it. Recurring weekly + a definable success signal.
Task is UNVALIDATED, so run #1 is a validation gate (below).

## Maturity rung
Current: 0→1. Validation gate baked into run #1; optimizes after.

## Four phases
- Trigger:      routine, Monday 08:00
- Execution:    new `linkedin-article` skill (research → draft in voice)
- Verification: Tier 4 + Tier 3 — Codex craft-judge pre-publish,
                real engagement post-publish. Judge != writer.
- State:        state.json — validated:false, then angle, hook, CTA,
                judge score, engagement (backfilled). Read each run.

## Measurement lag
Second loop: daily scraper backfills engagement by post id.

## Stop rule
Human publish gate (you approve) + hard cap on research iterations.

## Open risks
- Likes are a NOISY proxy for quality — timing/topic can spike a weak post.
  Don't let the loop treat a viral fluke as the gold standard.

Written — the full runnable construct:

loops/linkedin-article/skill/SKILL.md trigger.md state.schema.json state.json · validated:false verify.md · Codex judge scraper-loop.md stop.md README.md
The validation gate: run #1 (next Monday) researches + drafts one article, then stops and asks you "ship-worthy? y/n." Only on yes does validated flip to true and the loop start trusting its own scores. You get the whole machine today — it just proves itself once before it self-improves.
